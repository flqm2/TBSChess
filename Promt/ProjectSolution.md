# TBSChess 프로젝트 작업 원칙

## 1. 프로젝트 목적과 기준

- 이 프로젝트는 PPT 기획서에 담긴 전략 RPG 체스를 실제로 제작하기 위한 프로젝트다.
- 개발의 기준은 사용자가 제공한 기획서와 사용자의 명령이다.
- 이후 작업에서도 이 문서를 확인하고 아래 원칙을 지속적으로 적용한다.
- 작업을 시작할 때 `Promt/PRD.md`의 최신 내용도 함께 읽고, 사용자가 직접 수정한 요구사항·개발 순서·확인 사항을 반영한다.
- PRD의 5주 계획은 개발 지침이며, 사용자가 지시하지 않은 다음 단계의 기능을 자동으로 구현하는 허가가 아니다.
- 사용자가 별도로 승인한 이동·충돌·턴 프로토타입은 정식 게임과 구분하며 `Promt/Prototype.md`의 범위를 따른다. 진영당 2기, 총 4기를 사용한다.

## 2. 사용자가 지시한 범위만 구현

- 사용자의 명령에 따라 프로젝트를 점진적으로 제작한다.
- 사용자가 명령하지 않은 기능은 임의로 생각하여 추가하거나 구현하지 않는다.
- 필요해 보이는 기능이라도 사용자의 지시 없이 개발 범위를 확대하지 않는다.
- 사용자의 명령이 있더라도, 해당 내용이 기획서에 존재하지 않거나 기획서와 일치하지 않으면 구현하기 전에 반드시 다음 문구로 확인한다.

  > 이러한 명령이 지금 기획서와 일치하지 않습니다. 맞는지 확인 부탁드립니다.

- 확인을 요청할 때는 어떤 지시가 기획서에 없거나 어떤 부분이 다른지 함께 설명한다.
- 해당 내용은 사용자의 확인을 받은 후 작업한다.

## 3. 기획서 이미지 확인

- 기획서는 대부분 이미지를 사용하므로, 텍스트 추출만으로 내용을 파악했다고 판단하지 않는다.
- 구현할 내용과 관련된 기획서의 이미지를 직접 읽고 확인하는 과정이 필수다.
- 이미지에 담긴 규칙, 설명, 배치 및 예시를 함께 확인하여 지시와 기획서가 일치하는지 판단한다.
- 이미지를 읽을 수 없거나 내용을 판독할 수 없다면, 해당 작업을 진행하기 전에 읽지 못했다고 사용자에게 알린다.
- 읽지 못한 이미지의 내용을 추측하여 구현하지 않는다. 사용자가 글로 설명한 내용을 받은 후 해당 작업을 진행한다.

## 4. 단계별 개발

- 모든 개발은 한 단계씩 점진적으로 진행한다.
- 각 단계에서는 사용자가 지시한 작업 범위와 관련 기획 내용을 확인한 뒤 구현한다.
- 단계가 완료되면 변경 내용과 확인 결과를 사용자에게 설명한다.
- 현재 단계가 끝났다는 이유로 사용자가 명령하지 않은 다음 단계의 기능을 자동으로 개발하지 않는다.

## 5. 코드 구성

- 모든 구현을 `main.py` 하나에 몰아넣지 않는다.
- 클래스를 활용하고 역할에 따라 여러 파일로 나누어 구성한다.
- 파일과 클래스의 분리는 사용자가 요청한 기능을 구현하는 범위 안에서 진행하며, 구조를 나누기 위해 미요청 기능을 추가하지 않는다.

## 6. GitHub 저장

- 각 작업 단계가 완료되면 프로젝트의 GitHub 저장소에 변경 사항을 올린다.
- 변경 내용을 알 수 있도록 커밋 메시지와 작업 설명은 한국어로 작성한다.
- 해당 단계에서 작업한 파일을 확인하고 커밋한 뒤 원격 저장소에 푸시한다.
- 기존에 있던 사용자 변경 사항이나 관련 없는 파일을 임의로 포함하거나 덮어쓰지 않는다.
- 저장소 업로드에 실패하면 완료했다고 보고하지 않고, 실패 사실과 원인을 사용자에게 알린다.

## 7. 작업 순서

1. 이 문서와 사용자의 이번 명령을 확인한다.
2. 구현 작업이라면 관련 기획서의 텍스트와 이미지를 확인한다.
3. 기획서와 불일치하거나 기획서에 없는 지시는 구현 전에 사용자에게 확인한다.
4. 이미지 내용을 읽지 못했다면 작업 전에 알리고 사용자의 설명을 받는다.
5. 승인된 범위만 클래스와 여러 파일을 활용하여 한 단계씩 구현한다.
6. 해당 단계의 결과를 확인하고 한국어 설명으로 커밋하여 GitHub에 올린다.
7. 완료한 범위와 결과를 보고하고 다음 사용자 명령을 기다린다.
